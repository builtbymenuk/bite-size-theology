Deployment Runbook

Two apps, one server.
Everything else was detail.

How the Bite Size Theology website and its CMS admin got onto a single AWS Lightsail box — the six real steps, and the five things that fought back.

Lightsail · 2 GB · Debian 12 Next.js :3000 Strapi :1337 SQLite data.db

The mental model

A Lightsail instance is just a rented Linux computer. Deploying is four moves: get the code on it, install & build both apps, keep them running with a process manager, and open the firewall so the world can reach them. Hold that shape in your head and the rest is filling in blanks.

The pieces

Three things, and what each one is for.

Strapi
port 1337
Your CMS. Serves the /admin panel you edit in, and an /api the website reads from.
Next.js
port 3000
The public website. Fetches copy and images from Strapi and renders the pages.
SQLite
data.db · a single file
Strapi's database. Your content and uploaded images live inside it — so copying that one file is copying your data.

The deploy, step by step

Six steps, in order. This is the whole job when nothing goes wrong.

Log in over SSH

The key file you downloaded is your password. chmod 600 because SSH refuses a key other users could read.

local terminal
# lock the key down, then connect
chmod 600 sshbstt.pem
ssh -i sshbstt.pem admin@65.0.204.220

Ship the code

Rather than wrestle private-repo logins on the server, zip the folder — skipping the huge, rebuildable stuff — and copy it up. Keep data.db and uploads/ so your content travels with it.

local terminal
tar czf app.tgz --exclude=node_modules --exclude=.next --exclude=.git .
scp -i sshbstt.pem app.tgz admin@65.0.204.220:/home/admin/
# on the box: tar xzf app.tgz

Point the site at the server

One environment variable tells the website where Strapi lives. It was localhost for your laptop — change it to the server's public address so image URLs work in a real visitor's browser.

.env.local
STRAPI_URL=http://65.0.204.220:1337

Install & build both apps

Install dependencies, then compile each app for production. The admin panel and the website build separately.

on the box
# CMS
cd cms && npm ci && npm run build
# website — note the flag, see gotcha 2
cd .. && npm ci --include=dev && npm run build

Keep them running with pm2

A page will close, a crash will happen, the box will reboot. pm2 is a babysitter that restarts each app and brings them back after a reboot.

on the box
pm2 start npm --name strapi --cwd ./cms -- run start
pm2 start npm --name web -- run start
pm2 save && pm2 startup

Open the firewall

The one step SSH can't do — it's an AWS-account setting. In the Lightsail console → Networking, add two rules. Until this, the apps are running but sealed off.

Lightsail · Networking · IPv4 Firewall
Custom · TCP · 3000 · source Anywhere IPv4
Custom · TCP · 1337 · source Anywhere IPv4

And you're live:
Website → 65.0.204.220:3000
Admin → 65.0.204.220:1337/admin

The five things that fought back

Every first deploy is slow for the same reason: the six steps are easy, the environment's quirks are not. Here's what cost the time — and the one-line lesson from each.

◆ symptom · the box froze while building

The $5 server was too small

512 MB of RAM can't even build these apps — it ran out of memory and locked up hard enough to need a reboot. Even just starting Strapi exhausted it.

Lesson → builds are memory-hungry; give it 2 GB. Lightsail can't resize, so we rebuilt on a bigger box.

◆ symptom · Cannot find module '@tailwindcss/postcss'

The install skipped the build tools

Installing with production mode drops "dev" dependencies — but the website needs those very tools (Tailwind and friends) to build. So the build failed looking for something that was never installed.

Lesson → build with npm ci --include=dev, run in production.

◆ symptom · Strapi build crashed on a website config

Strapi grabbed the wrong config file

Building the admin panel, Strapi wandered up a folder and loaded the website's styling config by mistake.

Lesson → an empty cms/postcss.config.cjs tells it to stop searching upward. (Now committed to the repo.)

◆ symptom · the site quietly showed default content

The server couldn't call its own address

An AWS networking quirk ("hairpin") meant the box couldn't reach its own public IP — so the website's calls to Strapi failed silently and every page fell back to placeholder content.

Lesson → send the box's own traffic back to itself. A one-line network redirect (iptables → 127.0.0.1) fixed it.

◆ symptom · CMS edits didn't show up

The site was caching pages for 5 minutes

Next held each page for five minutes and served the stale one first — so an edit only appeared on the second reload, which reads as "nothing happened."

Lesson → for a live-editing demo, fetch fresh every load. Now an edit shows on a single refresh.

The takeaway

The deploy itself is genuinely six short steps. Nearly all the time went into environment-specific gotchas — which is normal, and exactly why the first deploy of anything is the slow one.

Do it once, write down what bit you, and the next deploy skips straight past all five. To edit content now: open the admin, hit Save, reload the website tab — it's there.
